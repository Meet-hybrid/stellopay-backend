# Challenge Nonce Generation and Expiry

This document describes the behavior and lifecycle of challenge nonces used for wallet ownership verification. 

## Overview
Challenges are short-lived, cryptographically random nonces (16 bytes, hex-encoded) generated by the backend and signed by a user's Starknet wallet. They are generated and managed primarily in `src/auth/challenge.ts`.

## Lifecycle
1. **Creation**: When a user initiates a login via `/auth/challenge`, `createChallenge(address)` generates a nonce and stores it in an in-memory Map, keyed by the wallet address. The default Time-To-Live (TTL) is 5 minutes.
2. **Retrieval**: Internally, `getChallenge(address)` returns the challenge for validation if it hasn't expired. If the TTL has passed, it deletes the expired challenge and returns `null`.
3. **Consumption**: When a wallet submits a signature for verification via `/auth/verify`, `consumeChallenge(address)` is called. This reads and deletes the challenge in a single atomic step to prevent a replay race condition. If successful, the signature is then verified.
4. **Clearing**: A challenge can be explicitly cleared using `clearChallenge(address)`.

## Telemetry and Metrics
Structured logging is emitted using `console.info()` as JSON strings. These logs are tagged with a `metric` key to allow downstream monitoring and debugging. The following metrics are exposed:

- `challenge_created`: Fired when a new challenge is generated. Includes `address`, `expires_in_ms`, and `timestamp`.
- `challenge_consumed`: Fired when a challenge is successfully retrieved and deleted for verification. Includes `address` and `timestamp`.
- `challenge_expired`: Fired when an expired challenge is lazily evicted upon retrieval. Includes `address` and `timestamp`.
- `challenge_miss`: Fired when a requested challenge does not exist (or has already been consumed). Includes `reason: "not_found"`, `address`, and `timestamp`.
- `challenge_cleared`: Fired when an active challenge is explicitly cleared. Includes `address` and `timestamp`.

## Rationale for In-Memory Retention
Challenges are highly transient. Storing them in-memory avoids unnecessary database read/write overhead for every unauthenticated challenge request. If the server restarts, the user's wallet client simply requests a new challenge nonce with no negative security implications and minimal friction.
