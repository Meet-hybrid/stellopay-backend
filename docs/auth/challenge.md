# Challenge Nonce Generation and Expiry

This document describes the behavior and lifecycle of challenge nonces used for wallet ownership verification.

## Overview
Challenges are short-lived, cryptographically random nonces (16 bytes, hex-encoded) generated by the backend and signed by a user's Starknet wallet. They are generated and managed primarily in `src/auth/challenge.ts`. The lifetime of a single challenge is owned by **exactly one address**: the Map key is `address.toLowerCase()`, so mixed-case retries for the same wallet collapse onto one record.

## Invariants

1. **At most one active challenge per address.** Issuing a new challenge for an address that already has an active entry is an idempotent replay — the existing nonce is returned, the TTL is **not** pushed forward, and a `challenge_replayed` metric is emitted instead of a fresh `challenge_created`.
2. **TTL is anchored to the original creation time.** Replaying `/auth/challenge` can never extend an attacker's window. After `CHALLENGE_TTL_MS` from the first issuance, the entry is treated as expired.
3. **The Map is the only source of truth.** There is no DB table, no Redis cache, no cross-instance replication. A server restart evicts every active challenge; clients retry by calling `/auth/challenge` again.
4. **Strict `>` TTL boundary (asymmetric between `getChallenge` and `createChallenge`).** Both functions use a strict `>` comparison against `expiresAtMs`, but the resulting behaviour differs:
   - `getChallenge`: at `Date.now() === expiresAtMs`, the record is still valid (the existing record is returned, not deleted).
   - `createChallenge`: at `Date.now() === expiresAtMs`, the record is treated as expired; the implementation falls through to the evict-and-create-fresh branch and issues a new nonce. The reasoning: at the boundary the record is on the verge of being useless to a verifier (the verifier's RPC round-trip alone usually crosses the boundary), and there is no benefit to handing back a single-millisecond-stale nonce when a fresh one is just as cheap to mint. The doc therefore reads "expires strictly **after** the recorded time" for the verifier side, and "expired strictly **at or after** the recorded time" for the issuer side.

## Lifecycle
1. **Creation / replay**: `createChallenge(address)` checks the Map for an active record on `address.toLowerCase()`. If one exists, it is returned with the time remaining on its TTL and a `challenge_replayed` metric is logged. Otherwise a fresh 16-byte random nonce is generated, the record is stored with `expiresAtMs = Date.now() + CHALLENGE_TTL_MS`, and a `challenge_created` metric is logged.
2. **Retrieval**: `getChallenge(address)` returns the challenge for validation if it hasn't expired. If the TTL has passed, it deletes the expired challenge and returns `null`.
3. **Consumption**: `consumeChallenge(address)` reads and deletes the challenge in a single atomic step. This is what `/auth/verify` calls immediately before the async signature check, so two concurrent verify requests cannot both pass verification off the same nonce.
4. **Clearing**: A challenge can be explicitly cleared using `clearChallenge(address)`.

## Idempotency contract

This is the surface that `#195` (idempotent login/challenge/session issuance) relies on:

| Operation                                   | Effect on retry within TTL | Effect on retry after TTL | Effect after consume |
| ------------------------------------------- | -------------------------- | ------------------------- | -------------------- |
| `createChallenge(address)` — first call      | creates new entry          | creates new entry         | creates new entry    |
| `createChallenge(address)` — retry          | returns same nonce (replayed) | creates new entry       | creates new entry    |
| `getChallenge(address)` — retry             | returns same record        | returns null (evicts)     | returns null         |
| `consumeChallenge(address)` — retry         | returns null on second call | returns null (evicts)   | returns null         |
| `clearChallenge(address)` — retry           | no-op, no log              | no-op, no log             | no-op, no log        |

A retry of `/auth/challenge` therefore **cannot** invalidate an in-flight verify attempt for the same address. This is what makes the route layer safe for at-least-once delivery from a flaky network or a walleted client retrying on a timeout.

## Telemetry and Metrics
Structured logging is emitted using `console.info()` as JSON strings. These logs are tagged with a `metric` key to allow downstream monitoring and debugging. The following metrics are exposed:

- `challenge_created`: Fired when a brand-new challenge is generated. Includes `address`, `expires_in_ms` (the full TTL), and `timestamp`. NOT emitted on a replay.
- `challenge_replayed`: Fired when `createChallenge` returns an already-active entry instead of issuing a fresh one. Includes `address`, `expires_in_ms` (the **remaining** TTL), and `timestamp`. Use this metric to track how often clients are retrying `/auth/challenge` inside the TTL window.
- `challenge_consumed`: Fired when a challenge is successfully retrieved and deleted for verification. Includes `address` and `timestamp`.
- `challenge_expired`: Fired when an expired challenge is lazily evicted upon retrieval. Includes `address` and `timestamp`.
- `challenge_miss`: Fired when a requested challenge does not exist (or has already been consumed). Includes `reason: "not_found"`, `address`, and `timestamp`.
- `challenge_cleared`: Fired when an active challenge is explicitly cleared. Includes `address` and `timestamp`.

## Rationale for In-Memory Retention
Challenges are highly transient. Storing them in-memory avoids unnecessary database read/write overhead for every unauthenticated challenge request. If the server restarts, the user's wallet client simply requests a new challenge nonce with no negative security implications and minimal friction.

## Out of scope (intentional non-goals)

- **Cross-instance replication.** A challenge issued by instance A cannot be consumed by instance B. The route layer does not retry across instances. If you need HA, route `/auth/challenge` and `/auth/verify` to the same instance via sticky sessions, or move challenges into a shared store — but that's a follow-up.
- **Proactive sweeper.** Expired entries are evicted lazily on `getChallenge` / `consumeChallenge` / a fresh `createChallenge` on the same address. There is no background timer that walks the Map; an unused address will keep its entry around for up to one TTL past expiry, then forever. This is acceptable because (a) addresses are bounded by user base and (b) the worst-case footprint per address is a few hundred bytes.
- **Rate limiting on `/auth/challenge`.** A caller that hits `/auth/challenge` in a tight loop will see the same nonce returned each time and emit one `challenge_replayed` per call. The rate-limit surface is `/auth/verify` and `/auth/login` upstream (see `src/middleware/rate-limit.ts`); the challenge endpoint is intentionally cheap.
- **Background `challenges.size` monitoring.** Expose a Prometheus gauge for the Map size only if memory pressure ever shows up; not part of this contract.

## Test hook

`clearChallengesForTesting()` is exported from `src/auth/challenge.ts`. It wipes the Map and is intended for unit tests in `src/auth/challenge.test.ts` and integration tests in `src/routes/auth.test.ts`. Production code MUST NOT call it — there is no compensating action for a deliberately-cleared challenge, and a single process eviction would invalidate any concurrent verify attempt for that address.
